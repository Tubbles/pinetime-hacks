## Clock-sync review findings (2026-08-02, code review of the v1 implementation)

- **Bug — reconnect resync is defeated by the outbound dedup cache.** `ClockSyncBridge.sendStopwatchFrame`/`sendTimerFrame` (fork `app/src/main/java/com/best/deskclock/clocksync/ClockSyncBridge.java:245-261`) record every dispatched frame in `mLastSentStopwatchFrame`/`mLastSentTimerFrame`, including frames broadcast while the watch link is down (the Intent API has no delivery queue, per the comment in `init()`, so those are lost). On `ACTION_ACL_CONNECTED` the `ConnectionReceiver` calls `resendCurrentState()`, which rebuilds a byte-identical frame for any unchanged paused/stopped/cleared state and the dedup suppresses it — the watch never converges. Fix: null out both `mLastSent*` fields in `ConnectionReceiver.onReceive` (or bypass dedup in `resendCurrentState`). Applies to the canonical `phone/clocksync/` copy too.
- **Firmware UX gap — screens go stale when a phone command lands while they are open.** `StopWatch::Refresh()` (`InfiniTime/src/displayapp/screens/StopWatch.cpp:218`) renders time by controller state but only the ctor and button handlers re-style buttons/wakeLock. A phone-initiated start while the screen shows "cleared" leaves the play icon and a disabled lap button while time ticks; tapping the visible ▶ then pauses. `Timer.cpp` has the same pattern (phone-start leaves the green "Start" button and +/- controls while the countdown runs; tapping "Start" stops it). The controllers stay correct — buttons act on real state — it is purely display staleness. Fix pattern: track the displayed state in `Refresh()` and call the existing `DisplayStarted/DisplayPaused/DisplayCleared` (resp. `SetTimerRunning/Stopped`) on change, same as the ctor does.
- **Inbound frames are not filtered by device address.** `ClockSyncReceiver` checks the characteristic UUID but ignores `EXTRA_DEVICE_ADDRESS`. Harmless with one watch; wrong if Gadgetbridge ever manages two InfiniTime watches. Cheap fix: compare against `clocksync_watch_mac`.
- **Exported receiver accepts forged broadcasts.** Any local app can send `CHARACTERISTIC_CHANGED` at the exported `ClockSyncReceiver` and start/stop the stopwatch or timer. Gadgetbridge's broadcasts are unsigned so there is no clean sender check; worst case is a nuisance timer. Accepted v1 risk — worth a line in the runbook.
- **Codec-drift guard.** `phone-codec.yml` tests the canonical `phone/clocksync/` codec; the shipping copy in the Clock fork can drift silently (they are identical today, verified by diff modulo the package line). Cheap guard: a diff step in `phone-app.yml` (which already checks out submodules) comparing the fork's `ClockSyncFrame.java` against the canonical one.
- **Threading note (no action).** `ClockSyncService::OnCommand` runs on the NimBLE host task and pokes `StopWatchController` fields the LVGL task reads. Worst case is one frame of torn display, and upstream services (MusicService) share the idiom; recorded so nobody rediscovers it as a mystery.
