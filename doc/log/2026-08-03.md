## [ble][gadgetbridge][infinitime] 2026-08-03 — the DFU flakiness, root-caused for real

The fourth DFU failure round finally broke the pattern: it failed with the usual `GATT REQ NOT SUPPORTED` (error 6) on the DFU control-point CCCD write, but this time on a completely fresh bond (BOND_NONE -> BONDED seconds earlier) with a genuine 2.6 s over-the-air service discovery in the log. That killed the runbook's "unpair clears the cache" advice — one lucky sample, not a mechanism — and forced the real forensics:

- **The error-6 semantics pinpoint the failure.** NimBLE returns `BLE_ATT_ERR_REQ_NOT_SUPPORTED` on a CCCD write only when the written flags are not allowed for that characteristic (`ble_gatts.c:710-712`). Writing 0x0001 (notify enable) can only be refused by an indicate-only characteristic — and the entire firmware has exactly one: Service Changed (`ble_svc_gatt.c:43`). So Android provably wrote the DFU enable at a handle where the watch keeps its Service Changed CCCD, i.e. the phone's handle table and the watch's disagree even after unpair + fresh discovery. Android's GATT cache simply cannot be trusted to be honest, whatever the bond state.
- **Why the tables kept diverging: two firmware sins.** (1) Our vendor services (ClockSync, KeyTones) registered BEFORE ANS/DFU/Battery/HR/Motion/FS in `NimbleController::Init()`, so every build shifted six stock services' handles. (2) InfiniTime never calls `ble_svc_gatt_changed()` — the spec's mechanism for telling bonded clients to drop their cache — anywhere. The Nordic DFU library even waits 4 s for exactly that indication on every connect ("Waiting 4000 ms for a possible Service Changed indication" in every DFU log) and InfiniTime never sends it.
- **Fixes, layered so no single component has to be trusted.** Gadgetbridge T (`32a74e101`): `BtLEQueue.refreshDeviceCache()` — the hidden `BluetoothGatt#refresh()`, same call as nRF Connect's "Refresh services" — invoked before every DFU start, so the flash never depends on cache honesty; the cache is per-device in the Bluetooth process, so the DFU service's own connection benefits. Firmware: vendor services now register LAST (stock handles restored to stock positions, future services append-only); a firmware fingerprint (`Version::GitCommitHash()` in `/fw_version.dat`) triggers `ble_svc_gatt_changed(0x0001, 0xffff)` on the first boot of a new firmware — live subscribers are indicated immediately, bonded-but-offline peers get NimBLE's persisted value_changed flag delivered on reconnect, and a client subscribing to Service Changed later in that boot session (fresh pairing with a stale cache) is told from the subscribe handler.
- **Bonus upstream bug (150fa3b6 "Persist bond between reboots"):** `PersistBond` read stored CCCDs with `key.cccd.idx = peer_count` — out of range every iteration — so `bond.dat` carried zeroed CCCD entries and the peer's subscriptions never actually survived a watch reboot. Fixed (`idx = i`); this is also the chain the Service Changed pending-flag delivery rides on, so the two fixes compose.
- The handle-shift fix moves our vendor services' handles one final time; the Service Changed announcement covers that transition itself. Candidate upstream contributions: the announcement, the CCCD idx fix, and the DFU cache refresh.

## [build] 2026-08-03 — CI signing round two: the keystore seeding never worked

The "app not installed" came back on the first attempted in-place update after the keystore fix. Verified by downloading the two runs' Gadgetbridge T artifacts and printing their signing certs (`keytool -printcert -jarfile`): three DIFFERENT certs — run one, run two, and the committed keystore all disagreed. So copying the keystore to `~/.android/debug.keystore` never took effect: AGP on the GitHub runner resolves its debug keystore somewhere else (its lookup goes through the Android tooling's own home-directory logic, not plainly `$HOME/.android`), found nothing there, and silently generated a fresh throwaway key per run. Silent fallback made the first fix look shipped when it wasn't — the artifact cert was never verified against the keystore. Lesson: after any signing change, verify the artifact's cert fingerprint against the intended keystore before declaring it fixed; "CI green" only proves it compiled.

Round two removes the guesswork: each fork's debug build type takes an explicit `signingConfig` from `PINETIME_DEBUG_KEYSTORE` (workflows export it pointing at `.github/debug.keystore`), and `PINETIME_CI_VERSION_CODE` (the workflow run number) gives CI builds `versionCode = base * 1000 + run` (bases: GB 251, Clock 2023, Phone 22), so an update can neither be refused for signature nor as a downgrade. Local builds without the env vars behave exactly as before. One more (final) uninstall/reinstall cycle is required for apps installed from pre-`d0b0a34` artifacts; the runbook heads-up carries the boundary.

## [infinitime][ble] 2026-08-03 — the real DFU killer: BLE host task stack overflow corrupting CCCD state

The probe build (GB T `4c49a7876`: GATT table dumps + DFU on a fresh ACL) delivered the decisive evidence and killed the stale-cache theory for good. The failing session's log shows a genuine over-the-air discovery, the dump of that fresh table — DFU control point `00001531` at handle 0x5a with props 0x18 (write|notify) and its CCCD present — and the notify-enable on that very CCCD still refused with error 6. **The watch rejects what its own table declares.** Since ATT error 6 on a CCCD write can only come from the clt_cfg entry's `allowed` field lacking the written bit (`ble_gatts.c:711`), and every legitimate writer of `allowed` is the one-time template fill (verified: template fill, per-connection memcpy, CCCD access and `ble_gatts_bonding_restored` mutate only `flags`), the per-connection CCCD table is being corrupted at runtime.

The corruptor (strong hypothesis, and the fix is correct engineering regardless): upstream's `PersistBond` (150fa3b6) puts ~750 B of `ble_store` unions on the NimBLE host task's stack — `union ble_store_value` is 72 B and `peer_cccd_set` holds BLE_STORE_MAX_CCCDS = 8 of them — and then calls littlefs (several hundred bytes more) on top of the GAP-dispatch call depth, in a task with a 720-word (2880 B) stack (`nimble_port_freertos.c`). It runs on EVERY disconnect with a bond present. A transient overrun stomps the adjacent heap allocation, which is the GATT clt_cfg pool (template + the single per-connection block, allocated moments after task creation). `configCHECK_FOR_STACK_OVERFLOW` was 1 (stack-pointer sample at context switch), blind to a spike that returns before the next switch. The phenomenology matches completely: intermittent error 6, degrades over reconnect-heavy sessions, heals on watch reboot, ATT table always correct, other subscriptions keep working.

Fixes: PersistBond's buffers are now static (host-task-only code, race-free) with an explicit memset; the host task stack grew to 1120 words (+1600 B); overflow checking is method 2 (canary). Diagnostic value of the probe stays: GB T dumps the served GATT table on every discovery, so any future cache-vs-watch dispute is a diff in one log.

Also found while reading: upstream MusicService registers `msTotalLengthCharUuid` at BOTH characteristicDefinition[6] and [7] (a pre-fork upstream bug, visible as duplicate UUID `00000007` in the GATT dump; the UUID-matched access callback makes track-number reads serve total-length data). Deliberately NOT fixed locally: stock 1.16.1 ships the duplicate, so keeping it preserves stock-identical handle positions. Upstream PR candidate.

Practical recovery lever while running pre-fix firmware: REBOOT THE WATCH (hold the button until reset), reconnect, and flash immediately — a fresh boot has an uncorrupted CCCD pool, and the corruption needs disconnect cycles to reappear.

## [infinitime][ble] 2026-08-03 — stack-overflow hypothesis REFUTED on-device; tripwire shipped instead

The falsification test was InfiniTime's own SystemInfo task page: the `ble` task's stack high-water mark, read on the running watch after the day's failing sessions, showed **223 words (892 B) minimum free** — nowhere near overflow, and the suspect path (PersistBond, which also runs at every bonded connection's encryption event, taking its full littlefs branch on the first call of each boot) had certainly executed inside that measurement window. The hypothesis from the previous entry is dead; its RAM-costing parts (the +1600 B host task stack, the static PersistBond buffers) are reverted. Kept on their own merits: `configCHECK_FOR_STACK_OVERFLOW 2` (free tripwire), the CCCD store idx fix, the Service Changed announcement, and the vendor-services-last layout.

What remains established, with no mechanism attached: the watch refused a CCCD notify-enable that its own freshly discovered table advertised (probe log, 2026-08-03 morning), the permission entry consulted at that moment disagreed with the table, and failures interleave with successes on identical firmware. Root cause: **unknown**.

Instead of hypothesis number four, the firmware now catches the culprit in the act: when NimBLE is about to refuse a CCCD write with REQ NOT SUPPORTED, it snapshots the connection's entire client-configuration table (handle/allowed/flags per entry, plus the refused request and a failure counter) into `ble_gatts_diag` (host/ble_gatt.h), readable via the new KeyTones diagnostic characteristic `00080003-78fc-48fe-8e23-433b3a1942d0`. Reproduction protocol: when a flash fails again, read that characteristic with nRF Connect (or the GB Intent API) and the corrupt bytes are on screen — the raw struct, last-writer-wins. Process lesson banked from this round: predictions were finally cheap to test because the watch already carried the instrument (SystemInfo); prefer on-device measurements over narratives from here on.

## [gadgetbridge][ble] 2026-08-03 — the flash that worked, and what it teaches

The user got the new firmware on via an unorthodox but mechanically sensible path: DFU initiated after a watch restart hung at "connecting"; they deleted the device in Gadgetbridge and began re-adding it; mid-PIN-entry the flash started on the watch and completed (PIN never finished). Explanation, all known behavior: Nordic's DfuBaseService is a standalone Android service with its own GATT client — GB's device list does not own it, so deleting the device does not abort a running DFU, and the service keeps retrying its connection in the background. The re-pairing flow brought up a live ACL to the watch, and the parked DFU client rode it the instant it existed. The DFU characteristics need no bond, so the unfinished pairing was irrelevant.

Operationally useful: a DFU stuck at "connecting" can be rescued by creating any link to the watch at all (even starting a pairing flow), and device deletion is NOT a way to cancel a flash. Also on the record, stated without a mechanism: this success — like earlier ones — happened on a maximally state-free path (fresh watch boot, no bond, no restored CCCD subscriptions), consistent with the still-unexplained pattern that fresh state flashes and accumulated state refuses. The tripwire characteristic (00080003) exists to turn the next refusal into data.

## [infinitime] 2026-08-03 — answering was blocked by the wrist-raise lock (user-diagnosed)

The unanswerable-call mystery was the lock screen, hypothesized by the user and confirmed in code: the incoming call rides the ordinary notification path (`Messages::OnNewNotification`), which never cleared the wrist-raise lock. The lock's design handled the alarm and the ringing timer as must-stay-interactive hazards and cleared the lock for an ESTABLISHED call (`CallStarted`) — but a RINGING call was the missed third instance, and it deadlocks beautifully: the answer tap is swallowed by the lock, and the unlock-on-CallStarted can never fire because answering is what triggers it. Also consistent with the "empty log" observation: swallowed taps generate zero BLE traffic, so nothing appeared at any hop. Fix: the OnNewNotification handler clears the lock when the arriving notification's category is IncomingCall; ordinary notifications stay view-only under the lock. Design doc's decisions list corrected. The 'A'-key answer path (previous entry) shipped before this root cause was found; it stays — it makes answering independent of Gadgetbridge's deprecated telephony call, which is failure-prone on its own record.

## [infinitime][ble] 2026-08-03 — evidence exhausted phone-side; on-watch BLE tracing shipped

Today's second DFU failure broke every remaining assumption: error 6 arrived while the CCCD-refusal tripwire stayed at zero (that path never ran), the failing write was on the Service Changed CCCD this time (which is at layout-stable handles and should accept 02-00), the unknown-opcode path can't produce it for a Write Request either — and the killer detail: the DFU revision characteristic is constexpr 0x0008 in the firmware, yet every session ever logged read 0x005d or 0x0051 from it. The phone has provably NEVER read the real attribute, including during successful flashes. Something is systematically wrong at a layer no phone log can see.

Shipped (InfiniTime `226c8eed`, user-requested deeper debugging): `components/trace` — a 256-record RAM ring hooked into every ATT error response sent (opcode/handle/error, in `ble_att_svr_tx_error_rsp` — one record answers "who sent the 6 and for which handle"), subscribe events, announces, GAP connect/disconnect/enc, bond persist/restore, DFU accesses (packet writes excluded), and the revision value actually served. Readout via `00080003`: write 0x01 = snapshot, 0x02 = snapshot + persist `/trace.bin`; reads page out ~200 B chunks until empty. `tools/decode_trace.py` decodes either `/trace.bin` or pasted nRF Connect hex. Protocol for the next failure: attempt flash -> write 0x01 to `00080003` -> read repeatedly until short/empty -> paste all hex to the decoder.
