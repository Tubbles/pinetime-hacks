# Log — 2026-09-14

## [infinitime] 2026-09-14 — the lock moved from the gesture to the wake

- User request opened a five-item "lock screen v2" package (`TODO.md`). Item 1 lands as InfiniTime `bafe5577`: every sleep → running transition locks the screen; the physical button is the only wake that comes up unlocked.
- The v1 axis ("motion wakes are the accidental ones") was wrong in the field sense: a pocket tap, an arriving notification, the hourly chime and a BLE-driven screen load hand a live touchscreen to a sleeve just as readily. Framing the rule as a property of the transition rather than of the gesture also collapses the implementation to one line inside `SystemTask::GoToRunning()`, which no call site has to know about.
- Useful identity found while doing it: `SystemTask::IsSleeping()` is `state != SystemTaskState::Running`, and `GoToRunning()` early-returns on `state == Running`. So "the body of `GoToRunning` executed" already means "we were asleep" — the `wasSleeping` capture the v1 motion branch carried was redundant even then.
- Gotcha that cost the most thought: **the timer-expiry clear now needs to exist in two places.** `DisplayApp`'s `TimerDone` handler clears the lock and then, only when its own state is not Running, pushes `System::Messages::GoToRunning`. The clear runs in the display task; the wake runs later in SystemTask and re-locks. So SystemTask's `Messages::GoToRunning` case gained a clear after the call. This directly inverts the 2026-08-02 correction, which argued that clearing there could never fire — true under v1 (the lock only existed while the display was Running), false under v2 (the wake itself creates the lock). Checked that `System::Messages::GoToRunning` has exactly one sender in the tree before making that case timer-specific.
- Same ordering trap, milder, everywhere else: `SetOffAlarm`, `CallStarted` and the incoming-call branch of `OnNewNotification` all used to clear the lock *before* waking. Under v2 the clear has to come after, or the wake it precedes re-locks it.
- Accepted fallout, not chosen: `OnChargingEvent` and wake-lock acquisition (`DisableSleeping`) are also sleep → running transitions and now lock. Neither screen needs touch.
- Known one-commit regression, closed by item 2: a notification wake now comes up locked, so the preview is view-only and a ringing call is unanswerable unless the incoming-call clear fires. The clear is still in place for this commit, so ringing calls stay answerable; the app-exemption item removes it.

## [infinitime] 2026-09-14 — exempt apps replace every lock clear

- InfiniTime `25b897de`. The lock's input gate and its button unlock-consume move from `SystemTask` to `DisplayApp`; the flag stays in `Settings`. Forced by the feature itself: the exemption is a statement about the frontmost app, and `currentApp` is DisplayApp's, not SystemTask's.
- Exempt while locked: `Apps::Notifications` and `Apps::NotificationsPreview`, `Apps::InCall`, `Apps::Alarm` while `alarmController.IsAlerting()`, `Apps::Timer` while `GetTimerState()->expired`. The lock survives the visit, so dismissing a notification or silencing an alarm lands back on a locked face.
- Amended user decision the same day: alarm and timer expiry no longer CLEAR the lock, they are dismissable under it. The old behavior left the watch unlocked after a 3 am alarm, which is the opposite of what the feature is for. Net effect: nothing clears the lock any more except a button press, sleep entry, and (next item) turning the feature off.
- **Gotcha 1, the one that would have shipped a silent bug.** Removing the SystemTask gate means `touchHandler.ProcessTouchInfo()` runs again on every touch while locked, so `TouchHandler::IsTouching()` is live instead of frozen false. The v1 design's "touch suppression precision" residual note explicitly relied on it being frozen to keep DisplayApp's continuous raw-coordinate path dormant. That path (`currentScreen->OnTouchEvent(x, y)` at the bottom of `Refresh()`) now needs its own lock check, or InfiniPaint and Paddle draw straight through the lock.
- **Gotcha 2.** `TouchHandler::gesture` is only cleared by `GestureGet()`. Dropping a touch event without calling it leaves a swipe made under the lock parked in the handler; a plain press reports gesture `None` and does not overwrite it, so the stale swipe fires on the first touch after unlocking. The gate calls `GestureGet()` and discards the result.
- Verified unchanged: the gate still sits before `lvgl.SetNewTouchPoint()`, the only writer of the state LVGL's indev callback reads, so LVGL sees no press and a locked screen still dims and sleeps on the inactivity timeout. `SystemTask::HandleButtonAction` pushes `NotifyDeviceActivity` before dispatching, so the unlocking press still resets that timeout even though DisplayApp consumes the action.
- Implementation note for future gates: four button messages needed the same guard, so it is a two-line `if (ConsumeButtonWhileLocked()) break;` at the top of each case rather than wrapping the 200-line message switch in an else.

## [infinitime] 2026-09-14 — padlock on the Timer screen

- InfiniTime `c22b23e4`. Same `DirtyValue<bool> lockedState` + `lv_obj_realign` pattern the three watch faces use; `AppTraits<Apps::Timer>::Create` now passes `settingsController`.
- The Timer is the app most likely to be raise-woken into, because the watch falls asleep on a running timer and the raise puts it straight back in front of you.
- Layout fact, contrary to the first guess: **the top-left corner is not free.** `minuteCounter` is aligned `LV_ALIGN_IN_TOP_LEFT` and `secondCounter` `LV_ALIGN_IN_TOP_RIGHT`, each roughly 100 px wide (`std::max(number width + 10, 58)` at `jetbrains_mono_76`) and ~186 px tall; the bottom 50 px is the start/pause button. The free space is the ~38 px strip between the counters, and the colon label below it is centered at y offset -29 so its top edge is well clear of y=0. The padlock goes `LV_ALIGN_IN_TOP_MID`.
- Decision: the padlock is driven by plain `IsLocked()`, not by DisplayApp's exemption predicate. So it also shows while the timer rings, a state that does accept touch. Rationale: it carries the same meaning as on a watch face (the watch is locked underneath and will still be locked afterwards), and the alternative would put a second copy of the exemption rule in a screen, free to drift from the real one.
- `Counter::HideControls()` only hides the +/- buttons, it does not resize the container, so the free strip is the same whether the timer runs or not.
