# Log — 2026-09-14

## [infinitime] 2026-09-14 — the lock moved from the gesture to the wake

- User request opened a five-item "lock screen v2" package (`TODO.md`). Item 1 lands as InfiniTime `bafe5577`: every sleep → running transition locks the screen; the physical button is the only wake that comes up unlocked.
- The v1 axis ("motion wakes are the accidental ones") was wrong in the field sense: a pocket tap, an arriving notification, the hourly chime and a BLE-driven screen load hand a live touchscreen to a sleeve just as readily. Framing the rule as a property of the transition rather than of the gesture also collapses the implementation to one line inside `SystemTask::GoToRunning()`, which no call site has to know about.
- Useful identity found while doing it: `SystemTask::IsSleeping()` is `state != SystemTaskState::Running`, and `GoToRunning()` early-returns on `state == Running`. So "the body of `GoToRunning` executed" already means "we were asleep" — the `wasSleeping` capture the v1 motion branch carried was redundant even then.
- Gotcha that cost the most thought: **the timer-expiry clear now needs to exist in two places.** `DisplayApp`'s `TimerDone` handler clears the lock and then, only when its own state is not Running, pushes `System::Messages::GoToRunning`. The clear runs in the display task; the wake runs later in SystemTask and re-locks. So SystemTask's `Messages::GoToRunning` case gained a clear after the call. This directly inverts the 2026-08-02 correction, which argued that clearing there could never fire — true under v1 (the lock only existed while the display was Running), false under v2 (the wake itself creates the lock). Checked that `System::Messages::GoToRunning` has exactly one sender in the tree before making that case timer-specific.
- Same ordering trap, milder, everywhere else: `SetOffAlarm`, `CallStarted` and the incoming-call branch of `OnNewNotification` all used to clear the lock *before* waking. Under v2 the clear has to come after, or the wake it precedes re-locks it.
- Accepted fallout, not chosen: `OnChargingEvent` and wake-lock acquisition (`DisableSleeping`) are also sleep → running transitions and now lock. Neither screen needs touch.
- Known one-commit regression, closed by item 2: a notification wake now comes up locked, so the preview is view-only and a ringing call is unanswerable unless the incoming-call clear fires. The clear is still in place for this commit, so ringing calls stay answerable; the app-exemption item removes it.

## [infinitime] 2026-09-14 — exempt apps replace every lock clear

- InfiniTime `25b897de`. The lock's input gate and its button unlock-consume move from `SystemTask` to `DisplayApp`; the flag stays in `Settings`. Forced by the feature itself: the exemption is a statement about the frontmost app, and `currentApp` is DisplayApp's, not SystemTask's.
- Exempt while locked: `Apps::Notifications` and `Apps::NotificationsPreview`, `Apps::InCall`, `Apps::Alarm` while `alarmController.IsAlerting()`, `Apps::Timer` while `GetTimerState()->expired`. The lock survives the visit, so dismissing a notification or silencing an alarm lands back on a locked face.
- Amended user decision the same day: alarm and timer expiry no longer CLEAR the lock, they are dismissable under it. The old behavior left the watch unlocked after a 3 am alarm, which is the opposite of what the feature is for. Net effect: nothing clears the lock any more except a button press, sleep entry, and (next item) turning the feature off.
- **Gotcha 1, the one that would have shipped a silent bug.** Removing the SystemTask gate means `touchHandler.ProcessTouchInfo()` runs again on every touch while locked, so `TouchHandler::IsTouching()` is live instead of frozen false. The v1 design's "touch suppression precision" residual note explicitly relied on it being frozen to keep DisplayApp's continuous raw-coordinate path dormant. That path (`currentScreen->OnTouchEvent(x, y)` at the bottom of `Refresh()`) now needs its own lock check, or InfiniPaint and Paddle draw straight through the lock.
- **Gotcha 2.** `TouchHandler::gesture` is only cleared by `GestureGet()`. Dropping a touch event without calling it leaves a swipe made under the lock parked in the handler; a plain press reports gesture `None` and does not overwrite it, so the stale swipe fires on the first touch after unlocking. The gate calls `GestureGet()` and discards the result.
- Verified unchanged: the gate still sits before `lvgl.SetNewTouchPoint()`, the only writer of the state LVGL's indev callback reads, so LVGL sees no press and a locked screen still dims and sleeps on the inactivity timeout. `SystemTask::HandleButtonAction` pushes `NotifyDeviceActivity` before dispatching, so the unlocking press still resets that timeout even though DisplayApp consumes the action.
- Implementation note for future gates: four button messages needed the same guard, so it is a two-line `if (ConsumeButtonWhileLocked()) break;` at the top of each case rather than wrapping the 200-line message switch in an else.

## [infinitime] 2026-09-14 — padlock on the Timer screen

- InfiniTime `c22b23e4`. Same `DirtyValue<bool> lockedState` + `lv_obj_realign` pattern the three watch faces use; `AppTraits<Apps::Timer>::Create` now passes `settingsController`.
- The Timer is the app most likely to be raise-woken into, because the watch falls asleep on a running timer and the raise puts it straight back in front of you.
- Layout fact, contrary to the first guess: **the top-left corner is not free.** `minuteCounter` is aligned `LV_ALIGN_IN_TOP_LEFT` and `secondCounter` `LV_ALIGN_IN_TOP_RIGHT`, each roughly 100 px wide (`std::max(number width + 10, 58)` at `jetbrains_mono_76`) and ~186 px tall; the bottom 50 px is the start/pause button. The free space is the ~38 px strip between the counters, and the colon label below it is centered at y offset -29 so its top edge is well clear of y=0. The padlock goes `LV_ALIGN_IN_TOP_MID`.
- Decision: the padlock is driven by plain `IsLocked()`, not by DisplayApp's exemption predicate. So it also shows while the timer rings, a state that does accept touch. Rationale: it carries the same meaning as on a watch face (the watch is locked underneath and will still be locked afterwards), and the alternative would put a second copy of the exemption rule in a screen, free to drift from the real one.
- `Counter::HideControls()` only hides the +/- buttons, it does not resize the container, so the free strip is the same whether the timer runs or not.

## [infinitime] 2026-09-14 — "Use lock screen" setting, and the SettingsData append trap

- InfiniTime `47a88ac3`. Persisted `lockScreenEnabled` (default true) gating the set in `GoToRunning()`, plus a Settings → Lock screen page with one checkbox. The clear-on-disable lives in `Settings::SetLockScreenEnabled`, not in the screen, so the invariant holds however the setting is reached.
- **The finding worth keeping.** "Append to `SettingsData` without bumping `settingsVersion`" is the project's standing rule, and it has a trap that would have bitten silently. `LoadSettingsFromFile` reads `sizeof(settings)` bytes into a default-constructed local and copies the whole struct in, so fields the (shorter) old file does not reach keep their NSDMI defaults. But a `bool` appended after the previous last member (`char intercomKey`) does not land past the old file: it lands in the **trailing padding of the previous layout**, inside the old file's length, and loads whatever byte that file carries there.
- Fix, and the pattern for every future append: `alignas(4)` on the first appended member. `SettingsData` is 4-byte aligned (it opens with `uint32_t version`), and trailing padding is by definition smaller than the alignment, so the first 4-aligned free offset is exactly the previous `sizeof`. Anything appended after that first member is beyond the old file too.
- Hand-computed layout for reference (ARM EABI, `enum class` without an underlying type is `int`-backed, `std::bitset<5>` is one 4-byte word): `brightLevel` is `enum class Levels { ... }` with no underlying type, so it is 4 bytes at offset 40, `dfuAndFsEnabledOnBoot` 44, `heartRateBackgroundPeriod` 46, `intercomKey` 48, three padding bytes, `sizeof` 52. Not compiler-verified, which is exactly why the fix is the alignment rule rather than a magic offset.
- Settings list grew to a fifth page (`nScreens` 4 → 5). `List` already skips `Apps::None`, and the `entries` array value-initializes its unfilled slots, so the three blanks need no other handling. Settings screens are wired through `DisplayApp::LoadScreen`'s switch and `src/CMakeLists.txt`, not through `UserApps.h`/`AppTraits` (that path is for launcher apps).

## [infinitime] 2026-09-14 — wrist gesture thresholds become sliders, and a research-doc correction

- InfiniTime `5ee0205c`. Eleven constants in `ShouldRaiseWake` and `ShouldLowerSleep` become persisted settings behind `lv_slider` rows on two pages (Settings → Raise wrist, Settings → Lower wrist), each with a Reset button. Sliders, not steppers, because the level knob spans 64–1024 and a +/- stepper would mean hundreds of presses. Full tables of knobs, defaults and ranges live in `doc/research-raise-wake.md`.
- **Correction to `doc/research-raise-wake.md`, found by reading the indexing carefully.** The shake-speed section claimed each delta was "the newest accelerometer sample minus the one ~800 ms ago (full ring buffer span)". It never was. `Utility::CircularBuffer::operator[](n)` returns `data[(idx + n) % S]` and `Update()` pre-increments `idx` before writing, so index 0 is the newest sample, index 1 is the OLDEST, and index `S - 1` is `data[idx - 1]`, the previous tick. The shake code reads `[histSize - 1]`, so it is a one-tick (~100 ms) delta. The `× 100 / (time - lastTime)` normalization is the tell: it divides by the interval between the last two samples, which only makes sense for a one-tick delta.
- That same indexing fact is why the ring could be resized from 8 to 16 without touching shake wake: `[size - 1]` is the previous tick whatever the size is. No separate constant needed, contrary to the first plan.
- `window` (the raise detector's look-back) was never a constant, it was the literal ring buffer size, and `settle` was `AccelStats::numHistory`. Both are settings now, indexing into a fixed 16-sample ring: "now" reads `[size - i]` for i < settle, "prev" reads `[size - window + 1 + i]`. With window 8 and settle 2 those resolve to exactly the indices the old 8-slot buffer produced, so the default behavior is bit-identical. Cost: 48 bytes of static RAM for the three wider buffers.
- `settle < window` is a cross-field invariant that two independent sliders can break, so it is clamped where the values are used (`ShouldRaiseWake`), not in the UI. Note that the clamp still permits overlap between the two groups at small windows (window 3 with settle 2 shares a sample); harmless, it just shrinks the measured roll.
- Lower wrist keeps its 8-sample timing deliberately: the same window sets the span of the history-floor scan, so a slider there would move two things at once. Its algorithm was undocumented before today and now has its own section in the research doc.
- `MotionController` stays free of any `Settings` dependency: the knobs arrive as `RaiseWakeThresholds` / `LowerSleepThresholds` plain structs that `SystemTask` fills per poll. The defaults live once in `components/motion/MotionThresholds.h`, included by both `Settings.h` and the settings screen, so the `SettingsData` initializers and the Reset buttons cannot drift.
- Both pages are one screen class (`SettingMotionThresholds`) that picks a row table and a pair of Settings accessors from a `Gesture` enum. Layout that fits 240x240 with six rows: title at the top, 29 px rows of a 122 px label ("name value", the 20 px font is ~12 px per character so ten characters is the budget, which is why the names are abbreviated) beside a 102 px slider, Reset button in the bottom 36 px.
- `Symbols::moon` (U+F186) was not in `jetbrains_mono_bold_20`; added to its FontAwesome range in `src/displayapp/fonts/fonts.json`, same move as the padlock on 2026-08-04. It comes from the same woff the weather font already pulls it from.

## [phone] 2026-09-14 — intercom auto-open mode in Phone T

- User request: arm "open the door automatically X times for the next Y hours" from the phone app, with the ring/answer/tone/repeat timings configurable. Landed as Phone T `8972894d` (engine + Settings section) and `5da43ed5` (the Intercom tab). Design, decisions and limitations: `doc/DESIGN-intercom-keytones.md` v2 section; setup and verification steps: the runbook section 5.
- Built with two Opus subagents in series (engine, then tab), each with a file allowlist and no build permission; reviewed and committed here. Nothing was compiled locally: Gradle OOMs this machine (user, same day), so CI is the compiler. The commons 6.1.0 AAR in `~/.gradle/caches` can be unzipped for `R.txt`, `res/` and `classes.jar` (`javap -constants` on `ConstantsKt`), which is how the tab bits, dialog inventory, view classes and styles were verified without a build.
- **`Config.showTabs` has exactly one writer, `ManageVisibleTabsDialog`.** So `ALL_TABS_MASK` is a true default: an install that never opened "Manage shown tabs" gets the new tab on update, one that did keeps its stored mask. The tab subagent reported the opposite ("existing installs have `showTabs` already stored"); grep says no.
- MainActivity carried two "the last tab is call history" assumptions (`initFragments` picks `tabCount - 1` for the missed-call notification launch; `setupTabs` clears missed calls on the last position). Both now use the call-history tab's index among the visible tabs. `getDefaultTab()` needed nothing: each of its indices is computed from the tabs before it, and the new tab is appended.
- Fossify commons ships no number-entry dialog (the 6.1.0 dialog inventory: RadioGroup, Confirmation, Rename, EnterPassword, ColorPicker, FilePicker, ...), hence the fork's `EnterNumberDialog` for the four timings; the key uses `RadioGroupDialog` over the twelve DTMF characters. Commons `TAB_*` bits run up to 64 (`TAB_STORAGE_ANALYSIS`, for other Fossify apps), so `TAB_INTERCOM` is 128.
- Engine facts worth keeping: the hooks are the same three `CallService` points `WatchCallState` uses; an opening is counted on the first ACTIVE transition (hold/unhold yields another ACTIVE, guarded by a flag), so a caller who gives up while ringing costs nothing and a manual answer before the ring delay still runs the tone sequence. The repeat loop is uncapped by the user's spec. There is no caller filter: every incoming call inside the window is the intercom (candidate follow-ups in `SUGGESTIONS.md`).
- Left alone: `viewPager.offscreenPageLimit = 2`, so with four tabs the intercom page can be destroyed while the contacts tab is up. Harmless, every refresh call is null-safe and the fragment re-reads its state on inflate.
