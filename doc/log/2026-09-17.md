# Log — 2026-09-17

## [ble][infinitime] 2026-09-17 — the trace read-out eats itself under Android long reads

- Another DFU failure (details still to come from the user). First attempt to pull the on-watch trace per the runbook, with nRF Connect at the default MTU: the WRITE 0x02 was acknowledged, the very first READ failed with `GATT INVALID OFFSET` (error 7), and every READ after that returned 74 bytes of zeros. The 74 is `sizeof(ble_gatts_diag)`: 2+2+2+1+1+1 bytes, two of padding, then 16 entries of 4, i.e. the legacy CCCD-refusal struct with the tripwire at zero, which `KeyTonesService::OnCallState` serves once `Trace::ReadChunk` has nothing left.
- Mechanism, read in the stack: `ble_gatts_val_access` (ble_gatts.c) calls the characteristic's access callback for EVERY read request, Read Blob continuations included, then copies `callback length - offset` bytes from `offset`, and answers `BLE_ATT_ERR_INVALID_OFFSET` when that is negative. Android issues a Read Blob whenever a read response is exactly MTU-1 bytes long. So at ATT MTU 23 a 200-byte page produces blob requests at offsets 22, 44, ... and each of them makes our callback hand out the NEXT page: the first read consumed pages 1-4 (a full 64-record ring is 776 bytes) and the fifth callback returned the 74-byte fallback against offset 88, hence error 7. One read drained the whole snapshot into garbage.
- Why it never showed before: earlier read-outs went through Gadgetbridge or an nRF Connect session that had already negotiated a large MTU, where 200 bytes fit in one response and no blob is issued. The protocol is correct only for MTU > 201.
- The watch's side of the negotiation: `MYNEWT_VAL_BLE_ATT_PREFERRED_MTU` is 256 in InfiniTime's NimBLE syscfg, so any client request above that lands at 256, still enough for a 200-byte page. The user's nRF Connect showed 517 somewhere, but the pasted log has no "MTU changed" line and the error-7 position (fifth callback, offset 88) is only reachable with 22-byte responses, so the link was at 23 during the read.
- Workaround, now in the runbook: Request MTU 517 in nRF Connect before the first read (the log must answer "MTU changed to: 256"), and re-snapshot with 0x01 if a read already failed (the ring is untouched by a snapshot; only the cursor resets). Proper fix, in `TODO.md`: page at most `ble_att_mtu(connHandle) - 2` bytes per callback, since the callback gets the connection handle and NimBLE exposes the negotiated MTU.
- Copying: nRF Connect's Log view exports as text; `tools/decode_trace.py` now extracts the `Read Response received from 00080003-...` lines from such an export by itself (the earlier strip-everything-but-hex parser would have swallowed timestamps, UUIDs and words like "Read" as hex).
- The 0x02 write did persist `/trace.bin` before the read-out went wrong, so the failed flash's records are on the watch's filesystem even if the RAM ring gets overwritten by the diagnostic session itself (nRF Connect's connect, subscribe and error records land in the same 64-slot ring).

## [ble][infinitime][flash] 2026-09-17 — DFU failure root-caused: the CCCD store is full, and NimBLE reports that as ATT error 6

- Evidence: `/trace.bin`, persisted by the 0x02 write and pulled off the watch with the new `tools/pull_watch_file.py` (laptop `hci0`, bleak, the BLE FS read protocol). It holds the failed flash itself: DFU revision read, then 2.6 s later `SUBSCRIBE reason=1 handle=0x004e notify=1` (the DFU control point) and, in the same tick, `ATT_ERROR_TX opcode=0x12 handle=0x004f error=0x06` (the control point's CCCD). The subscription WAS established and the phone still got "Request Not Supported". 150 s of silence, then the phone dropped the link. On the next connection the bond restored exactly 8 CCCDs (`reason=3`: 0x0008 indicate, plus 0x1e 0x48 0x54 0x5b 0x5f 0x68 0x72 notify), the DFU one not among them.
- Mechanism, each step in the vendored NimBLE: `ble_gatts_clt_cfg_access` (ble_gatts.c) applies the CCCD write, fires the subscribe event, THEN persists it with `ble_store_write_cccd` and returns that call's status as the access result. The RAM store (`ble_store_ram.c`, installed from `main.cpp`) holds `BLE_STORE_MAX_CCCDS` = 8 entries (syscfg.h) and answers `BLE_HS_ESTORE_CAP` to the ninth. `ble_store_write` (ble_store.c) turns ESTORE_CAP into an overflow event; the configured handler `ble_store_util_status_rr` tries `ble_gap_unpair_oldest_except(current peer)` to make room, and with the phone as the only bonded peer that returns `BLE_HS_ENOMEM`, which is 6 (ble_hs.h). `ble_att_svr_write` copies a non-zero callback result straight into the ATT error byte, and ATT error 6 is REQUEST NOT SUPPORTED. Nordic's DFU library treats it as fatal.
- Why it looked like cache corruption for two months: the CCCD table was always correct (the tripwire on the `allowed` check never fired, because that check passes), the phone's handles were right, and the subscription even succeeded. The error is manufactured after the fact by the persistence layer, from a code that has nothing to do with ATT.
- Why intermittent, and why this fork: stock InfiniTime gives the phone about 6 notify/indicate characteristics to subscribe to; this fork's ClockSync and KeyTones notify characteristics bring Gadgetbridge T to 8, which fills the store exactly, so the DFU control point is always the ninth. Before 2026-08-03 the bond's CCCDs never survived a reboot (the `idx = peer_count` bug), so a fresh boot started with an empty store and the first flash after a reboot fit: the "successes cluster after fresh boots" pattern. The 2026-08-03 idx fix made the restore work, which is why the item was reopened on 2026-08-11: the store is now full from the first connection after boot. The recovery firmware flashes because it has its own, empty, store.
- Second, independent bug found on the way: `DfuService.cpp` passes `&revision` as the revision characteristic's `.val_handle`. NimBLE writes the attribute handle into that pointer at registration, so the served "revision" is the characteristic's own handle (0x0051 now, 0x005d in the old layout), never the constexpr 0x0008. This is the August observation "the phone has never read the real attribute". Harmless for the DFU library (0.81 still passes its version gate) but wrong, and upstream.
- Fix plan, in `TODO.md`: (1) in `ble_gatts_clt_cfg_access`, a failed persist must not fail the write (the subscription is live for this connection either way; a DFU session never needs it persisted); (2) optionally raise `BLE_STORE_MAX_CCCDS`, but `PersistBond` puts `MAX_CCCDS` copies of the 72-byte `ble_store_value` union on the host task stack, so switch that buffer to `ble_store_value_cccd` first; (3) the revision `val_handle` bug; (4) the trace read-out paging by MTU; (5) stop tracing the discovery terminators (ATT error 0x0a on opcodes 0x04 and 0x08), 30 records per discovery in a 64-slot ring. To get the fixed firmware on: the running firmware will refuse the DFU CCCD again, so flash it through the recovery firmware (button held on boot until the pine cone is red), whose store is empty.

## [infinitime][flash] 2026-09-17 — the fixes, and what the persist patch changes for other peers

- Landed as InfiniTime `50b477ef` (persist failure no longer fails the CCCD write, traced as type 8), `2ae6b7ed` (DFU revision `val_handle`), `0591f122` (read-out paged by `ble_att_mtu(connectionHandle) - 2` with a 20-byte floor; discovery terminators, ATT error 0x0a on opcodes 0x04/0x06/0x08/0x10, no longer traced). Built by CI only; on-device confirmation is the recovery-firmware flash and then a few ordinary OTA flashes.
- The patch sits after `ble_store_write_cccd` in `ble_gatts_clt_cfg_access`, so NimBLE's overflow handling still runs first: `ble_store_util_status_rr` evicts the OLDEST OTHER bonded peer to make room. With the phone as the only bond that is a no-op, but a second bonded peer (a laptop paired for the trace pull, say) would be unpaired silently by the ninth CCCD. `tools/pull_watch_file.py` does not pair (the FS characteristics need no encryption), so it does not create that situation.
- `<algorithm>` has to be included after the NimBLE headers in `KeyTonesService.cpp`: they `#define min`/`max` and only undefine at the end of the InfiniTime header that wraps them. clang-format realigned the `Trace.h` enum comments when the new entry became the longest; cosmetic, but it is why that file's diff is seven lines wider than the change.

## [infinitime] 2026-09-17 — error visibility: event log, watch notifications, log screen

- User decision after the DFU root cause: "do all of your error visibility suggestions". Design record: `doc/DESIGN-error-visibility.md`. Landed as InfiniTime `8097da9a` (event log component, the DFU and CCCD sites, boot line, notifications) and `e3aefaf3` (Settings -> Event log screen, three lines per page). Two Opus subagents in series, CI-only builds.
- `-Wformat-truncation=2 -Werror` is on for the firmware targets (`src/CMakeLists.txt`), and it rejects a `snprintf` whose `%s` the compiler cannot bound. The logger therefore formats only the timestamp with integer directives and copies the text by hand, and every call-site format gives its `%s` a precision (`%.16s` for the hash and reset reason, `%.9s` for the DFU state). `DateTime::FormattedTime` looks like an existing counter-example, so the warning may not have fired, but the precautions are free.
- `DfuService::Reset()` never stops the 10 s timeout timer, so a timer started by a stray characteristic access, or by the CRC-error path, fires after the transfer is already Idle. The timeout event is therefore reported only when the state is not Idle. Found by the subagent while placing the site; the spec had said "notify unconditionally".
- A mid-transfer disconnect reaches the DFU service only through that timeout: `NimbleController`'s disconnect handling resets the time and alert clients, not the DFU service. So "DFU timeout in Data at N %" is the line for a phone that walked away, and the percentage is the only clue how far it got.
- Stack, not static: the logger keeps three pointers and nothing else; the 96-byte line buffer, the `lfs_file_t` and the 264-byte `lfs_info` of the rotation check live in separate frames so they never coexist. The recovery firmware target links the logger too (its source list carries the trace), so it logs its own DFU events.
- Notification shape reused from the file-transfer service's access-denied alert: title, NUL, body, NUL, size counting both terminators, category SimpleAlert, then `Messages::OnNewNotification` to the system task. Pushed from the BLE host task, which is where the ANS notifications already come from.
