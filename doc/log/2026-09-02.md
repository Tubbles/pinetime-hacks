# Log — 2026-09-02

## [infinitime] 2026-09-02 — G7710 upcoming-alarm indicator

- Bell + HH:MM right of the heart-rate/padlock slot while the native alarm is armed and due within 24 h (InfiniTime `14cb1561`). User decisions from the design questions: watch-native alarm only (phone alarms would need GB T plumbing), placement right of the padlock slot with the heart-rate value taking priority while displayed, and always-24h formatting regardless of the clock-type setting.
- The 24 h window only does real work for Weekdays recurrence (Friday evening → Monday alarm stays hidden); Daily and one-shot armed alarms are always within it. `AlarmController::SecondsToAlarm()` is unsigned and can wrap huge while the alarm is ringing (alarmTime just passed); the wrap fails the window check and merely hides the indicator.
- Pattern note for tight faces: the indicator packs armed+time into one `DirtyValue<uint16_t>` (minutes-of-day, 0xFFFF sentinel = none), initialized to the sentinel so an armed 00:00 alarm still paints on the very first refresh. `Symbols::bell` (U+F0F3) was already in the `jetbrains_mono_bold_20` FontAwesome range — no font work needed.

## [build] 2026-09-02 — firmware CI broke without a source change; build image now pinned

- The upcoming-alarm commit failed CI in `littlefs/lfs.c` — a file untouched since the last green build. Evidence chain: CI pulls `infinitime/infinitime-build` un-tagged (= `latest`); Docker Hub shows `latest` re-pushed 2026-08-17 (between our green 2026-08-12 run and the failure); upstream commit `4f7b430c` that day is "Update GCC (in doc and docker) to GCC15.3". GCC ≥ 14 turns implicit function declarations into hard errors in C, and littlefs v2.4.1's `LFS_DEBUG` → NRF-log macro chain lands on a nonexistent `LOG_INTERNAL_7` under the new toolchain. Verified NOT our change: the failing translation unit is a pinned submodule.
- Fix: pin the image to `infinitime/infinitime-build:sha-f882df9` (2026-03-20, GCC 10.3) — the image every green build actually used; upstream tags images by commit sha, so the pin is stable. Applied in `firmware.yml` and the CLAUDE.md build command.
- Standing lesson: `latest` for a toolchain image is a time bomb; the un-pinned reference had been silently relying on upstream not moving. If the fork base is ever bumped toward upstream main, revisit the pin (upstream main builds with GCC 15; our 1.16.1 base does not without porting).
