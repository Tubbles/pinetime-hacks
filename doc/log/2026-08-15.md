## [gadgetbridge] 2026-08-15 — BLE Intent API settings seed themselves on first connect

- User ask: stop re-entering the Intent API settings after every reinstall/re-add. GB T `fe6a6c3d3` seeds the deployment values (both switches, key-tones characteristic filter, Phone T package filter) into the PineTime's device prefs in `PineTimeJFSupport.setContext`, BEFORE the superclass consults `BleIntentApi.isEnabled`, so the first connect of a fresh install already runs with the API on.
- Design decision worth remembering: prefilling via pref-read-site defaults was rejected because `Prefs.getList` treats an empty string exactly like an absent key — a read-site default would resurrect after a deliberate clear, and an empty filter legitimately means subscribe-to-everything. Seed-once-with-marker preserves stock semantics for every later edit and clear; only never-set keys are filled, so upgrading an install with customized values changes nothing.
- Restore-to-defaults path: removing the device deletes its device-specific prefs (`AbstractDeviceCoordinator.java:224`), so remove-and-re-add re-seeds. Runbook section 2 rewritten: the Intent API steps are now verify-or-change, not enter.
