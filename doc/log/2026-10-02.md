## [phone] 2026-10-02 — reading Perfetto traces from the phone: the lag is memory thrashing

- Context: after a GrapheneOS update the phone lags in waves (10 to 20 s of multi-second input latency, then a few seconds of speed). The user recorded two System Tracing sessions on the phone (Pixel 9a "tegu", build CP3A.260905.009, Android SDK 37, 7.3 GB RAM, 3.66 GB zram swap).
- Tooling that works on this laptop: the `perfetto` PyPI package (`uv venv tmp/perfetto-venv && uv pip install --python tmp/perfetto-venv/bin/python perfetto`) downloads the native `trace_processor_shell` on first use and exposes SQL over the trace. `nix build nixpkgs#perfetto` does NOT work today: it fails compiling against the current abseil (btree_map template errors), so do not wait for it.
- Trace 1 (77 KB) was empty of events: System Tracing had no categories selected, so the 114 MB ftrace buffer received zero bytes and only the process list survived. Trace 2 (20 MB, categories sys_stats, mq, cpu, wattson, logs) carried PSI, meminfo, vmstat at 1 s, a 100 Hz CPU sampler, and Chromium track events, but still no scheduler events (needs "sched") and no per-process memory (needs "memory"). The 24-minute trace bounds are a Chromium artifact; the service's own clock says the session was 90 s (`tracing_started_ns` to `tracing_disabled_ns`).
- GrapheneOS specifics seen in the trace: the CPU sampler produced not a single callstack (every sample has no callsite, no unwind error), so the unwinder cannot read process memory there, and the `android.log` data source captured nothing from logd (the four lines present are Chromium's own), so lmkd kills are invisible. Process names for processes that exit during the session stay null.
- The finding, from the 90 s window: MemAvailable between 8 and 190 MB, swap full to within 0 to 18 MB, zram holding 3.66 GB in 800 MB, anonymous memory 3.5 to 3.6 GB resident, kswapd0 at 35 CPU-seconds, 100 000 to 120 000 major page faults per 10 s at the peaks, 50 to 70 MB/s re-read from flash, PSI memory "full" 20 % and IO "full" 32 % of wall time. The vmstat buckets alternate heavy (0 to 30 s, 50 to 70 s) and calm (40 s, 70 to 90 s), which is the wave the user feels. Diagnosis: the resident working set of the running apps exceeds the RAM, and reclaim thrashes. Not CPU contention: none of Gadgetbridge T, Phone T or YACB T appears in the top 25 CPU consumers (each under 1.3 CPU-seconds in 90 s).
- Heaviest CPU users in the window, for the record: kswapd0 (the symptom), the Claude Android app (the Chromium "Browser" process whose threads are named `//claude.ai/...`, with its WebView renderer, about 23 CPU-seconds, loading pages with 15 to 29 s TCP connects because the phone was thrashing), an unnamed process spawned alongside it (19 CPU-seconds), Beeper (15), system_server (19), surfaceflinger (13). Sixty app processes were alive.
