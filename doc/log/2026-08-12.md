# Log — 2026-08-12

## [gadgetbridge] 2026-08-12 — replay-missed-notifications already exists in stock GB, dismissal pruning included

- User ask: queue notifications that miss the watch (disconnected) and replay on reconnect, skipping ones already dismissed on the phone; fallback idea was an age cap if dismissal isn't visible phone-side. Source read of GB T (base 0.92.2) found the whole thing already implemented and merely off by default — no fork work needed.
- The pieces, verified at source: pref `notification_cache_while_disconnected` ("Cache while out of range" in Notification settings) gates a per-device Intent cache in `DeviceCommunicationService` (`:828-837`), capped at `NOTIFICATIONS_CACHE_MAX = 10` with oldest-evicted; phone-side dismissal reaches `NotificationListener.onNotificationRemoved` (`:1028`), whose delete request prunes matching cached entries by notification id while the device is away (`DeviceCommunicationService.java:838-849`); the cache flushes through the normal send path when the device reaches initialized (`:436-438`, `sendCachedNotifications` `:1605`).
- So dismissal IS visible phone-side (Android `NotificationListenerService.onNotificationRemoved`, long wired up in GB), and the age-cap fallback is unnecessary. The cache-while-away gate `isDeviceReconnecting` (`:1378`) is misleadingly named: it is `state >= NOT_CONNECTED`, true for any registered device, so caching works whenever the watch is out of range regardless of reconnect state.
- Known trade-offs (stock behavior, acceptable for now): the reconnect flush sends everything back-to-back, so up to 10 buzzes in a row; the cache is process-memory, lost if Android kills the GB service while the watch is away. If the buzz burst proves annoying in the field, fork options are rate-limiting the flush or trimming the replay count.
- The toggle is now part of the standard GB T configuration in the runbook, section 2.
