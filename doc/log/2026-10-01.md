# Log — 2026-10-01

## [phone] 2026-10-01 — regex call-screening rules, and what Fossify's "drag" adapters actually do

- User request: an ordered stack of block/allow regex rules over the canonical (+46…) caller number. Landed as Phone T `5414fa36`; design in `doc/DESIGN-call-screening-rules.md`. One Opus subagent, CI-only build.
- Semantics decided from the user's own example (`blacklist .*` then `whitelist +46.*` should block abroad): **the last matching rule wins**, no match allows. First-match-wins would have made the example's second rule dead. Patterns match the whole number (`Regex.matches`), so anchoring is implicit.
- Hook point: `SimpleCallScreeningService.onScreenCall`, a new branch between Fossify's blocked-number list and its block-unknown switch. The service is only consulted while the app holds the call-screening role, which Android grants through `setDefaultCallerIdApp()` (the "caller ID and spam app" prompt); the rules screen requests it the first time the list is non-empty. Without the role the rules silently do nothing, which is why the role request is tied to the feature and not to app start.
- **Fossify adapter gotcha:** `MyRecyclerViewAdapter.setupDragListener(true)` is drag-to-SELECT (multi-select by dragging across rows), not reorder. Reordering goes through commons' `ItemTouchHelperContract` (`onRowMoved`/`onRowSelected`/`onRowClear`) driven by `ItemMoveCallback` in an `ItemTouchHelper`, and `ItemMoveCallback` returns false for both `isLongPressDragEnabled` and `isItemViewSwipeEnabled`, so a drag can only start from an explicit handle via `StartReorderDragListener.requestDrag`. The `ContactsAdapter` in this app is the precedent; `SpeedDialAdapter` is not reorderable at all.
- Second adapter gotcha: `ManageSpeedDialActivity` rebuilds its adapter on every change. Copying that with an `ItemTouchHelper` would attach a new helper (an `OnItemTouchListener` plus an `ItemDecoration`, never removed) to the same `RecyclerView` each time. One adapter per activity, refreshed with `notifyDataSetChanged`.
- Selection keys are `System.identityHashCode`, not `hashCode()`: two rules may be value-equal, and the speed-dial adapter's value hashing would merge them in the action mode.
- `PatternSyntaxException` is an `IllegalArgumentException` subclass, so one catch clause covers both; a second would be unreachable.
- Canonicalization reuses `Config.regionHint` (SIM country, then network country, then locale) and `PhoneNumberUtils.formatNumberToE164`, the same path the custom-SIM lookup takes, with `Uri.decode` and the `tel:` strip first so a percent-escaped `+` in the handle reaches the rules as `+`. A number E.164 cannot parse falls back to `normalizeNumber` so the service still answers.
- Same-day follow-ups from the user, each its own commit: a notification per blocked call (Phone T `ad7c26e5`, number and rule, silent channel at default importance like the app's other channels); then a hidden-number switch on the rules screen and blocked calls in the call history with a show-all/hide/only filter (Phone T `f1c7aeca`).
- Why the hidden-number switch is new UI for an old pref: Fossify's own "block hidden numbers" switch lives in commons' Compose blocked-numbers screen, which Phone T gates behind the "Thank you" paywall dialog (`SettingsActivity.setupManageBlockedNumbers`), so it was unreachable in this build. The rules screen exposes the same `blockHiddenNumbers` pref.
- Why the call history needs no storage of its own: `CallScreeningService.CallResponse.setSkipCallLog(false)` makes Android write the blocked call itself with `Calls.BLOCKED_TYPE` (API 24, this app's minimum is 26), presentation included, so hidden-number blocks show as "Unknown" with the blocked icon. The app only renders the type and ANDs a `Calls.TYPE` clause into the recents query for the filter. `setSkipNotification(true)` stays: it only suppresses the system's missed-call entry, and the app's own notification replaces it. Fossify's blocked-number list keeps skipping the log, so its blocks stay invisible as before.
