## [design][hub] 2026-10-27 — Hub T and the printer finish time in the next-event corner: what the research settled

- Ask: the 3D printer's estimated finish time in the G7710 corner that already shows the next alarm (feature 11), with an icon, the sooner of the two winning, fed by a new phone app that will later host more integrations ("smart apps" whose logic runs on the phone). Design and the user's four decisions (bitmap icon in the frame, 15-minute WorkManager polling, keep the last time when the host is unreachable, home Wi-Fi only with no Moonraker account): `doc/DESIGN-hub.md`.
- The watch side was already reserved: `doc/DESIGN.md` (Napper, parked) allocated vendor service id `0006` and a phone-written next-event characteristic. The Hub service takes that id and generalizes it to several sources, each with its own 1-bit icon. `0007` is ClockSync, `0008` KeyTones (their `CharUuid` bodies in `src/components/ble/`).
- Write-only on purpose: the bond's CCCD store (8 entries) is full since 2026-09-17, so the event characteristic has no notify and no CCCD. The remote-app input channel, which will need one, is the only reason to spend an entry later.
- Transport needs no Gadgetbridge T change: `BleIntentApi.java` accepts a CHARACTERISTIC_WRITE from any package, checking only the device address and the initialized state; the notify-side package and characteristic filters do not apply to writes. The device-level "Allow GATT interaction" switch is already seeded on (`fe6a6c3d3`). Gadgetbridge T requests MTU 256 (`PineTimeJFSupport.java:673`) and the watch prefers 256 (`MYNEWT_VAL_BLE_ATT_PREFERRED_MTU`), so an 86-byte frame fits one write.
- The reconnect trigger is the system `ACTION_ACL_CONNECTED` broadcast, as in the ClockSync bridge: Android's implicit-broadcast exemption list includes it, so a manifest receiver gets it without a running process. Gadgetbridge's own `BLUETOOTH_CONNECTED` fires exactly when the device is initialized (`DeviceCommunicationService.java:437`) but goes out implicit and gated by the global `PREF_ALLOW_INTENT_API` switch, so a manifest receiver never sees it. Writes before initialization are refused, hence the delayed re-send after the ACL event, with every periodic poll as the fallback re-send.
- Icon format: `lv_conf.h` enables `LV_IMG_CF_INDEXED` and disables `LV_IMG_CF_ALPHA`, so the corner icon is an indexed-1-bit `lv_img` with a two-entry palette, not an alpha mask. LVGL's image cache (6 entries) must be invalidated when the bitmap under a descriptor changes.
- Moonraker on fluiddpi: `[authorization]` has `force_logins: True` with `trusted_clients` covering `192.168.0.0/16` and `10.0.0.0/8` (homelab `moonraker.conf.j2`). Moonraker's docs: force_logins overrides trusted clients only once a user has been created, and untrusted clients authenticate with `X-Api-Key`. The user has no account, so the phone on the home Wi-Fi needs no key. The Nexa plug powers the printer and the Pi together (homelab `doc/printer-power.md`), so "printer off" is "host unreachable".
- ETA inputs verified against the Moonraker docs: `print_stats.state` (standby, printing, paused, complete, error, cancelled), `print_stats.print_duration` (seconds, pauses excluded), `display_status.progress` (from M73, falls back to `virtual_sdcard.progress`), file metadata `estimated_time` in seconds. Klipper keeps no slicer remaining-time value, so the app computes its own.
- Memory: four event slots are about 350 bytes of static RAM, charged to the ~39 KiB heap per the 2026-08-10 lesson; accepted. A full RGB565 frame (115,200 bytes) does not fit anywhere, which fixes the shape of the later remote-app channel as strips straight to the LCD controller.
- Later the same day: Hub T's settings are the printer URL and the poll interval (default and floor 15 minutes, WorkManager's minimum); the watch address is baked in as Clock T does, so there is no credential and no address to type.

## [flash][infinitime][ble] 2026-10-27 — flashing from vaio: a DFU start request hangs a sleeping watch

- The user put the watch next to vaio and asked for the Hub firmware (InfiniTime `2f6252b3`, Firmware run 40504976333) to be flashed from there. `tools/dfu_flash.py` (new) speaks the watch's legacy DFU over BlueZ with bleak and never pairs. NimBLE persists CCCDs for bonded peers only (`ble_gatts_clt_cfg_access`), so the full bond store never comes into it.
- The first two attempts failed at the first control point write (StartDFU) with ATT error 0x0e. Each time the link dropped, the watch stopped advertising, and it came back from a watchdog reset: two `reset=Watchdog` boot lines in /events.log, and the RAM trace began at a fresh boot. The 0x0e is BlueZ's own: `process_error` in BlueZ 5.72 `src/shared/gatt-client.c` returns `BT_ATT_ERROR_UNLIKELY` when a request ends without an error PDU, that is on timeout or link loss. The watch never answered.
- Cause: `DfuService::ControlPointHandler` logs "DFU start" on the NimBLE host task before it pushes `BleFirmwareUpdateStarted`, the message that wakes the system task. A sleeping watch has its NOR flash in deep power down and its SPIM disabled (`SystemTask.cpp`, the OnDisplayTaskSleeping branch), so the littlefs access in `EventLog`'s `AppendLine` never completes: `SpiMaster::Write` waits for an END event that a disabled SPIM never raises. The handler stopped there: neither attempt left a "DFU start" line, though logging it is the handler's first action in Idle. How the stuck host task turns into a watchdog reset was not traced; the reset came roughly two minutes after the first attempt's write. The hazard arrived with the event log (`8097da9a`, 2026-09-17).
- The same path serves the "DFU image" line (the Start-state packet, logged before the handler waits for the wake), the wrong-state line, and the bond store failure line from `ble_gatts.c`. Every Gadgetbridge flash writes the last one (its DFU subscription is the ninth for eight entries), so a phone flash started on a sleeping watch hangs it the same way. The one phone flash since `8097da9a` (2026-09-17 16:31 in /events.log) went through, which fits a watch that was awake then. Fix: TODO point 3; until it lands the runbook says to wake the watch before a phone flash.
- The workaround that confirmed the cause: a one-byte read through the file-transfer service right before StartDFU. `FSService::FSCommandHandler` pushes `StartFileTransfer` and waits while the system task sleeps, so the watch is running when the start request lands, and `BleFirmwareUpdateStarted` keeps it awake from there. With that step the same request went through and the flash completed: 404640 bytes in 20-byte packets with a receipt every 10 packets, 330 s on vaio's adapter. Packets must be 20 bytes, since `DfuImage::Init` refuses any other chunk size and `Append` asserts on longer writes.
- Stale TODO: the watch has run `e3aefaf3` since 2026-09-17, and that build contains the three DFU fixes the TODO called "not yet flashed". /events.log shows its boot, then a phone flash at 16:31 that logged "CCCD 0x004e not saved" and still completed (the persist fix at work), then its boot again. Neither that day's log nor the TODO recorded the flash. TODO corrected.
- Outcome: after the activate the watch advertised again within 19 s, and a fresh discovery from vaio listed the Hub service (`00060000`, write-only `00060001`), which only `2f6252b3` has. The image stays unvalidated until the user validates it on the watch. The user then took the watch, so the new boot line in /events.log was not read.
