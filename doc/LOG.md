## [gadgetbridge] 2026-07-19 — BLE Intent API removes the need for a GB fork

- Gadgetbridge 0.82.0 (Sep 2024) shipped a documented BLE Intent API: any local app broadcasts `nodomain.freeyourgadget.gadgetbridge.ble_api.commands.CHARACTERISTIC_WRITE` with device MAC + characteristic UUID + hex payload, and GB writes it over its existing watch connection. Enabled per device under Developer settings. This is the transport: no GB fork, keep the F-Droid build.
- Gotchas to design around (from FederAndInk's calendar prototype): Android's GATT service-discovery cache hides a newly added characteristic until the watch is removed and re-added in GB; large writes need MTU raised (our payload is tiny, so likely fine); no delivery queue, so re-send on GB's `BLUETOOTH_CONNECTED` broadcast.

## [infinitime][gadgetbridge][build] 2026-08-01 — clock sync research done, design drafted

- Design: `doc/DESIGN-clock-sync.md`. Three legs: InfiniTime ClockSync BLE service (fork), stock Gadgetbridge Intent API (both directions), forked clock app.
- InfiniTime: both stopwatch and timer already run in the background (StopWatchController is a survives-navigation global; Timer fires via a FreeRTOS software timer regardless of screen; Alarm is the third precedent). The only refactor: promote `Controllers::Timer` from a DisplayApp member to a `main.cpp` global so a NimbleController-owned service can reach it (StopWatch/Alarm are already globals). No new background machinery needed.
- Gadgetbridge: the BLE Intent API carries BOTH directions. Write (phone->watch) plus subscribe+rebroadcast (watch->phone) via a second toggle. Because `addService` runs for every discovered GATT service before the "supported services" gate, a brand-new InfiniTime characteristic works with NO PineTimeJFSupport fork. Both legs since 0.82.0; per-characteristic filtering since 0.84.0. Trap: the CHANGED event extra is `EXTRA_CHARACTERISTIC` (not `_UUID`, which is the write/read command extra); the public gadgetbridge.org docs get this wrong.
- Clock app: `com.android.deskclock` is AOSP DeskClock; GrapheneOS ships an integration fork (`GrapheneOS/platform_packages_apps_DeskClock`, per-Android-version branches like `16-qpr2`). ":37" is a platform-injected build number, not a stable app version. Stock external surface is inadequate (timer create-only via SET_TIMER, no public stopwatch intent, exact times locked in a notification chronometer), so a fork is required. Can't replace the platform-signed system app: rename the package and install as a user app; upstream is Soong-only so port sources to a Gradle project. GrapheneOS: BLE Intent API toggles are a restricted setting for sideloaded apps ("Allow restricted settings" first).
- Vendor service ID: ClockSync = `00070000-...`; `0006` reserved for the parked Napper next-event service.
- Sync design: state transitions + wall-clock reference only (InfiniTime RTC is CTS-synced), full idempotent snapshots, last-writer-wins, resend-on-connect; never per-tick.

## [infinitime] 2026-08-02 — CORRECTION: timer-expiry lock-clear must live in DisplayApp

- The previous entry said the timer-expiry hazard was fixed by clearing the lock in SystemTask's `System::Messages::GoToRunning` case. That clear could never fire: DisplayApp only pushes the message when the display is not Running (`DisplayApp.cpp:376-378`), and the wrist-raise lock can only exist while the display IS Running (raise-wake sets it, every sleep entry clears it). ## [infinitime][gadgetbridge][ble] 2026-08-02 — first on-device session: three real bugs, all fixed

Field testing after the flash found three independent bugs. Two were Android-platform realities the design had not accounted for; one was ours.

- **Clock T crashed on watch-initiated timers (ours).** BlackyHawky's `addTimer` takes a 4th `buttonTime` argument that the timer list renders with `Long.parseLong`; the bridge passed `""`, so `TimerItem.update` threw `NumberFormatException` the moment such a timer appeared, killing the process and the bridge with it. That is what made sync look one-directional and flaky. Fixed (Clock `43bb963c8`) by using `SettingsDAO.getDefaultTimeToAddToTimer`, the same value the intent-API path passes. Lesson recorded in the canonical copy as a comment: buttonTime is a stringified number of MINUTES, never empty.
- **Outgoing calls never opened the InCall screen (platform).** Gadgetbridge derives `CALL_OUTGOING` from the `NEW_OUTGOING_CALL` broadcast (`PhoneCallReceiver.java:55-56,99-100`, registered at `DeviceCommunicationService.java:1423`), which Android 11 removed — so on Android 17 it emits nothing for phone-initiated calls, and Gadgetbridge T's forwarding had nothing to forward. Fix: the call state now originates in Phone T, whose `InCallService` sees every call (outgoing and VoIP included), and is written to the watch through Gadgetbridge's Intent API (Phone `60d5d668`). Ringing is still not reported as in-progress, so it does not fight the incoming-call screen.
- **Hang-up did nothing during an established call (platform).** The watch's ANS Reject reaches `TelecomManager.endCall()` (`GBCallControlReceiver.handleCallCmdTelecomManager`), deprecated since API 29 and evidently refused for the ongoing call; Gadgetbridge swallows both failure paths with a log line, so it fails silently. Its own deprecation note says wearable companions should use the InCallService API — which we now have. Fix: the watch also sends `'E'` on the key characteristic (InfiniTime `23e308b4`); Phone T maps it to `CallManager.reject()`, which handles ringing (`call.reject()`) and established (`call.disconnect()`) explicitly. Both paths are kept: the ANS reject still serves a ringing call answered from the notification screen.
- Diagnostic note: the DTMF keys working while hang-up failed was the decisive clue — they are different paths (keys go watch -> Clock T -> Phone T, hang-up went watch -> Gadgetbridge -> Telecom), which is what separated a platform bug from a transport bug.

## [infinitime][ble] 2026-08-02 — ClockSync epoch skew: the watch RTC runs on local time

The user's second field report ("sync only goes watch -> phone, stopwatch play/pause never comes back") led to a full re-audit of the phone->watch write chain. Every transport link checked out in source — Clock T's listener fires on every `StopwatchModel.setStopwatch`, the dedup cache cannot swallow a state transition, GB T registers its command receiver `RECEIVER_EXPORTED` and `addService` puts *every* discovered service's characteristics in the Intent-API map (not just supported ones, `AbstractBTLESingleDeviceSupport.java:294-297`), the hex codecs agree, and the control characteristic is plain `BLE_GATT_CHR_F_WRITE`. The real, proven bug was in the time base:

- **The frame's `reference_epoch_ms` is defined as UTC** (phone uses `System.currentTimeMillis()`), but the firmware's `NowMs()` used `DateTime::CurrentDateTime()` — and the CTS-synced RTC runs on *local* time (Gadgetbridge writes local wall clock plus a separate Local Time characteristic with tz/DST offsets, `PineTimeJFSupport.onSetTime`). At UTC+2 every phone->watch timer computed `remaining = reference - now_local` = real remaining *minus two hours* -> negative -> silent `StopTimer()`: nothing visibly happens. Watch->phone timers came out two hours too long, and a phone-started stopwatch would jump to 2:00:00. Fix: `NowMs()` now uses `DateTime::UTCDateTime()`, which subtracts those offsets; all four epoch uses (parse + both frame builders) share the helper, so one line fixed both directions. If the offsets were never written, `UTCDateTime()` degrades to the old behavior (offset 0), so stock-GB pairing is unaffected.
- The design doc even said "UTC milliseconds; InfiniTime's RTC is CTS-synced so both sides share this base" — a half-truth that caused the bug: CTS syncs the RTC to *local* time, so the shared base requires the explicit UTC conversion. Doc corrected in both places.
- Diagnostic caveat for next time: logcat captures of GB T and Clock T contain *no* application log lines (GB logs via slf4j/logback to its own file, and the bridge only logs on dropped frames), so they cannot prove whether an Intent-API write arrived. The tool for that question is GB T's own file log (Settings -> "Write log files"), which records `BLE API write` transactions and `Characteristic ... not found` errors. If phone->watch still fails after this fix, one such log of a single phone-side play press settles where the frame dies.

## [gadgetbridge][ble] 2026-08-02 — stuck at "Connecting": one failed GATT action bricked init

Third field round: InCall now auto-opens (first on-device proof that an Intent-API WRITE lands), but after entering the BLE Intent API settings the user could no longer reconnect — Gadgetbridge T stayed at "Connecting" while the watch showed the link as up, and only a re-pair recovered. In that half-state key tones still worked while hang-up, auto-open, and everything phone->watch died together, which looked like a wholesale regression but is a single failure:

- **Mechanism (all verified in GB 0.92.2 source):** any GATT action failing aborts the rest of its transaction (`BtLEQueue.checkWaitingCharacteristic`), and the "Initializing device" transaction ran the BLE Intent API's notify subscriptions BEFORE the device support's own init — whose last step is what sets `State.INITIALIZED`. One failed CCCD write therefore left the device in INITIALIZING forever. The asymmetric symptoms are exactly the gates in the code: `CHARACTERISTIC_CHANGED` forwarding has no initialized-check (and the watch persists CCCD subscriptions in the bond, so notifications flow immediately on reconnect), while Intent-API writes refuse a non-initialized device (`BleIntentApi:89`) and GB does not dispatch native commands to one either. Tones-work-but-writes-dead IS the fingerprint of a device stuck in INITIALIZING.
- **Fixes (GB T fork):** the init transaction now runs `initializeDevice()` first and the Intent-API subscriptions after, so a failed subscription costs that characteristic's notifications instead of the whole connection; and `BleIntentApi.initializeDevice` skips characteristics without NOTIFY/INDICATE properties, so write-only characteristics in the filter (or a wildcard/empty filter, which subscribes to everything) no longer create GATT actions that can only fail.
- **Runbook corrected:** the characteristic filter had listed the write-only ClockSync control char `00070001`. The filter governs notify subscriptions only; it must list just `00070002` and `00080001`. Which action actually failed on-device is still unproven (the logcat captures contain no GB application logging) — GB T's file log ("Write log files") records `failed btle action, aborting transaction: <uuid> <status>` if it happens again.
- **InCall UX (user request):** the physical button in the keypad view now backs out to the main in-call view (mirroring the existing right-swipe) instead of leaving the app.
- Open loose end: hang-up staying dead while tones worked also fits the stuck-INITIALIZING state for the ANS leg, but the 'E'-key leg (watch -> Clock T -> Phone T `CallManager.reject()`) rides the exact same ungated pipe as the working digits and needs no Gadgetbridge dispatch — so if hang-up still fails after a healthy connect, the prime suspect is the installed dialer APK predating the 'E' handling (`60d5d668`, first shipped in the `84c195a` CI run).

## [build] 2026-08-02 — "app not installed": CI debug APKs were signed with throwaway keys

Updating Gadgetbridge T from a fresh CI artifact failed with Android's bare "app not installed". Not a versionCode problem (Android reinstalls the same versionCode over itself fine): every GitHub-hosted runner is ephemeral, AGP generates a brand-new `~/.android/debug.keystore` when none exists, and Android refuses to update an app whose signing key changed. So no CI-built APK could ever update a previously installed one — every update would have needed a full uninstall.

Fix: a debug keystore generated once with the standard Android debug parameters (alias `androiddebugkey`, storepass/keypass `android`, `CN=Android Debug,O=Android,C=US`) is committed at `.github/debug.keystore`, and all three Android workflows copy it to `~/.android/debug.keystore` before Gradle runs. AGP picks it up with the default debug credentials, so zero Gradle changes in any of the three forks (all their debug build types use default debug signing; their custom signingConfigs only activate for release with a `keystore.properties`). Committing a debug key with well-known passwords is standard practice for reproducible debug builds; it must never be used for release signing.

One-time migration cost: apps installed from pre-keystore artifacts carry a throwaway signature, so each needs one uninstall + fresh install (GB T loses pairing + settings, Clock T alarms/timers, Phone T the default-dialer role). Recorded in the runbook heads-up.

## [ble][gadgetbridge][infinitime] 2026-08-03 — the DFU flakiness, root-caused for real

The fourth DFU failure round finally broke the pattern: it failed with the usual `GATT REQ NOT SUPPORTED` (error 6) on the DFU control-point CCCD write, but this time on a completely fresh bond (BOND_NONE -> BONDED seconds earlier) with a genuine 2.6 s over-the-air service discovery in the log. That killed the runbook's "unpair clears the cache" advice — one lucky sample, not a mechanism — and forced the real forensics:

- **The error-6 semantics pinpoint the failure.** NimBLE returns `BLE_ATT_ERR_REQ_NOT_SUPPORTED` on a CCCD write only when the written flags are not allowed for that characteristic (`ble_gatts.c:710-712`). Writing 0x0001 (notify enable) can only be refused by an indicate-only characteristic — and the entire firmware has exactly one: Service Changed (`ble_svc_gatt.c:43`). So Android provably wrote the DFU enable at a handle where the watch keeps its Service Changed CCCD, i.e. the phone's handle table and the watch's disagree even after unpair + fresh discovery. Android's GATT cache simply cannot be trusted to be honest, whatever the bond state.
- **Why the tables kept diverging: two firmware sins.** (1) Our vendor services (ClockSync, KeyTones) registered BEFORE ANS/DFU/Battery/HR/Motion/FS in `NimbleController::Init()`, so every build shifted six stock services' handles. (2) InfiniTime never calls `ble_svc_gatt_changed()` — the spec's mechanism for telling bonded clients to drop their cache — anywhere. The Nordic DFU library even waits 4 s for exactly that indication on every connect ("Waiting 4000 ms for a possible Service Changed indication" in every DFU log) and InfiniTime never sends it.
- **Fixes, layered so no single component has to be trusted.** Gadgetbridge T (`32a74e101`): `BtLEQueue.refreshDeviceCache()` — the hidden `BluetoothGatt#refresh()`, same call as nRF Connect's "Refresh services" — invoked before every DFU start, so the flash never depends on cache honesty; the cache is per-device in the Bluetooth process, so the DFU service's own connection benefits. Firmware: vendor services now register LAST (stock handles restored to stock positions, future services append-only); a firmware fingerprint (`Version::GitCommitHash()` in `/fw_version.dat`) triggers `ble_svc_gatt_changed(0x0001, 0xffff)` on the first boot of a new firmware — live subscribers are indicated immediately, bonded-but-offline peers get NimBLE's persisted value_changed flag delivered on reconnect, and a client subscribing to Service Changed later in that boot session (fresh pairing with a stale cache) is told from the subscribe handler.
- **Bonus upstream bug (150fa3b6 "Persist bond between reboots"):** `PersistBond` read stored CCCDs with `key.cccd.idx = peer_count` — out of range every iteration — so `bond.dat` carried zeroed CCCD entries and the peer's subscriptions never actually survived a watch reboot. Fixed (`idx = i`); this is also the chain the Service Changed pending-flag delivery rides on, so the two fixes compose.
- The handle-shift fix moves our vendor services' handles one final time; the Service Changed announcement covers that transition itself. Candidate upstream contributions: the announcement, the CCCD idx fix, and the DFU cache refresh.

## [infinitime][ble] 2026-08-03 — the real DFU killer: BLE host task stack overflow corrupting CCCD state

The probe build (GB T `4c49a7876`: GATT table dumps + DFU on a fresh ACL) delivered the decisive evidence and killed the stale-cache theory for good. The failing session's log shows a genuine over-the-air discovery, the dump of that fresh table — DFU control point `00001531` at handle 0x5a with props 0x18 (write|notify) and its CCCD present — and the notify-enable on that very CCCD still refused with error 6. **The watch rejects what its own table declares.** Since ATT error 6 on a CCCD write can only come from the clt_cfg entry's `allowed` field lacking the written bit (`ble_gatts.c:711`), and every legitimate writer of `allowed` is the one-time template fill (verified: template fill, per-connection memcpy, CCCD access and `ble_gatts_bonding_restored` mutate only `flags`), the per-connection CCCD table is being corrupted at runtime.

The corruptor (strong hypothesis, and the fix is correct engineering regardless): upstream's `PersistBond` (150fa3b6) puts ~750 B of `ble_store` unions on the NimBLE host task's stack — `union ble_store_value` is 72 B and `peer_cccd_set` holds BLE_STORE_MAX_CCCDS = 8 of them — and then calls littlefs (several hundred bytes more) on top of the GAP-dispatch call depth, in a task with a 720-word (2880 B) stack (`nimble_port_freertos.c`). It runs on EVERY disconnect with a bond present. A transient overrun stomps the adjacent heap allocation, which is the GATT clt_cfg pool (template + the single per-connection block, allocated moments after task creation). `configCHECK_FOR_STACK_OVERFLOW` was 1 (stack-pointer sample at context switch), blind to a spike that returns before the next switch. The phenomenology matches completely: intermittent error 6, degrades over reconnect-heavy sessions, heals on watch reboot, ATT table always correct, other subscriptions keep working.

Fixes: PersistBond's buffers are now static (host-task-only code, race-free) with an explicit memset; the host task stack grew to 1120 words (+1600 B); overflow checking is method 2 (canary). Diagnostic value of the probe stays: GB T dumps the served GATT table on every discovery, so any future cache-vs-watch dispute is a diff in one log.

Also found while reading: upstream MusicService registers `msTotalLengthCharUuid` at BOTH characteristicDefinition[6] and [7] (a pre-fork upstream bug, visible as duplicate UUID `00000007` in the GATT dump; the UUID-matched access callback makes track-number reads serve total-length data). Deliberately NOT fixed locally: stock 1.16.1 ships the duplicate, so keeping it preserves stock-identical handle positions. Upstream PR candidate.

Practical recovery lever while running pre-fix firmware: REBOOT THE WATCH (hold the button until reset), reconnect, and flash immediately — a fresh boot has an uncorrupted CCCD pool, and the corruption needs disconnect cycles to reappear.

## [infinitime][ble] 2026-08-03 — stack-overflow hypothesis REFUTED on-device; tripwire shipped instead

The falsification test was InfiniTime's own SystemInfo task page: the `ble` task's stack high-water mark, read on the running watch after the day's failing sessions, showed **223 words (892 B) minimum free** — nowhere near overflow, and the suspect path (PersistBond, which also runs at every bonded connection's encryption event, taking its full littlefs branch on the first call of each boot) had certainly executed inside that measurement window. The hypothesis from the previous entry is dead; its RAM-costing parts (the +1600 B host task stack, the static PersistBond buffers) are reverted. Kept on their own merits: `configCHECK_FOR_STACK_OVERFLOW 2` (free tripwire), the CCCD store idx fix, the Service Changed announcement, and the vendor-services-last layout.

What remains established, with no mechanism attached: the watch refused a CCCD notify-enable that its own freshly discovered table advertised (probe log, 2026-08-03 morning), the permission entry consulted at that moment disagreed with the table, and failures interleave with successes on identical firmware. Root cause: **unknown**.

Instead of hypothesis number four, the firmware now catches the culprit in the act: when NimBLE is about to refuse a CCCD write with REQ NOT SUPPORTED, it snapshots the connection's entire client-configuration table (handle/allowed/flags per entry, plus the refused request and a failure counter) into `ble_gatts_diag` (host/ble_gatt.h), readable via the new KeyTones diagnostic characteristic `00080003-78fc-48fe-8e23-433b3a1942d0`. Reproduction protocol: when a flash fails again, read that characteristic with nRF Connect (or the GB Intent API) and the corrupt bytes are on screen — the raw struct, last-writer-wins. Process lesson banked from this round: predictions were finally cheap to test because the watch already carried the instrument (SystemInfo); prefer on-device measurements over narratives from here on.
